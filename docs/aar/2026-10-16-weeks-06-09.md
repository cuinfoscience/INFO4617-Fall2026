## 5. Gap analysis (Q3)

### 5.1 Facts stated in several places drift apart (P0)

**Root cause: missing.** No file says which facts are repeated, or where. `AUTHORING.md` covers deck mechanics. The textbook's `decisions.md` lists where some decisions are applied ("Where. `ch-01-introduction.qmd`, `README.md`, `AGENTS.md`, the course's `handouts/week-01/setup.md` …"), and that list is exactly what made the `tesseract` change complete in the textbook. Nothing like it exists for this repository's own facts: grade weights, due dates, the Final Project parts, and code copied from chapters. Evidence: the four corrections in §4, each found late. The syllabus–Canvas split had been wrong since Canvas was first built; it only surfaced when an unrelated change touched the same file.

### 5.2 Claude's standing rules have no home in this repository (P0)

**Root cause: missing.** The rules that governed every merge and pull request in this window are not written anywhere a new session reads. They exist only in the instructor's chat instructions and in compaction summaries:
- the one-branch rule and the merge procedure;
- never touching students' pull requests;
- the image and privacy rules;
- attribution;
- handling downloads as untrusted.

They held this time, because each summary restated them. But the session was compacted four times, and the weeks 06–08 sessions ran elsewhere. One rule already conflicts with the written contract: `AUTHORING.md` says "rebase", the instructor's rule says merge `main` and never rebase. In this session the conflict was settled by remembering the instruction, not by reading a file. The textbook has an `AGENTS.md`; this repository is where the same agent does most of its slide work.

### 5.3 `AUTHORING.md` contradicts four things the course now does (P0)

**Root cause: contradictory.**
- **(a) Friday's section.** The section is defined as "Textbook Revisions — 3 frames". The last three Fridays were 12, 18 and 10 frames under three other titles, each from a plan or a decision by the instructor.
- **(b) Frame counts.** The ranges were exceeded again (§2a). A number copied from last month's decks keeps going stale.
- **(c) Rebase.** "Rebase rather than fight" conflicts with the merge rule in §5.2.
- **(d) Daily-note-questions.** The contract puts these on Friday. Weeks 07 and 08 kept them on Friday; week 09's, which the instructor added, opens Wednesday.

A contract that disagrees with the decks in four places teaches the next deck to ignore the contract.

### 5.4 Two of the four standing items have no check, and lapsed (P1)

**Root cause: buried.** "Effort over perfection" and "Error flavors" are standing rules in `AUTHORING.md`, but only in prose in the middle of the voice section. Weeks 07 and 09 omit both, and week 10 omits "Error flavors". The one item with a checker held across all three taught weeks. It's possible these two items are now situational, since Fridays no longer revolve around filing issues. That is the instructor's call, as P1-1 asks.

### 5.5 Placeholders reach class (P1)

**Root cause: missing check.** `AUTHORING.md` correctly keeps placeholders until there's a real capture, but nothing flags them before class. Week 05 was taught with one. Week 10 still has five, three days before class; one was replaced on request on 2026-10-16. (A first scan counted unused placeholder files in weeks 07 and 08 too; their decks don't include them.) `check_daily_questions.py` shows the shape of the fix: a pre-class check that names what is missing in the coming week's deck.

### 5.6 After-class steps in the Friday plan are skipped (P1, textbook)

**Root cause: buried.** The plan's §5 step ("regenerate the notebooks on `main` once") lives in a plan document, not in anything run at merge time. Four merged browser-made pull requests left the textbook's notebook check red on `main` until a separate request fixed it. A follow-up request to remind those authors to edit the source assumed they had edited the notebooks; they had edited the source, and the step the plan assigns to after class was what had been skipped. This one belongs to the textbook repository and is noted here because the Friday workflow is the course's.

- **Change:** create `AGENTS.md`:

  > # Working in this repository (for coding agents)
  >
  > This repo holds INFO 4617's slides (`slides/`), handouts, syllabus, Canvas tooling (`canvas/`), and process docs (`docs/`). The textbook is a separate repo, `cuinfoscience/Web-Data-Science-Book`; slides copy its code and figures. Deck rules are in `slides/common/AUTHORING.md`. This file covers how to work.
  >
  > **Branches and pull requests.** Work on one branch, start it from fresh `origin/main` (Overleaf pushes to `main` without warning), and open a pull request for each change. Follow the PR description pattern of recent PRs: what changed, why, what was checked, and what was left alone.
  >
  > **Merging.** Merge only when the instructor asks, with a merge commit and the expected head SHA. Before merging, check that CI passed (unless told to skip it), that the description has no closing keyword you didn't intend, and whether `main` moved. If it did, merge `main` into the branch — don't rebase or force-push, because the branch is already shared. After merging, confirm the merge commit's tree equals the branch's, and reset the branch to `main` for the next change.
  >
  > **Students' work.** Never edit, merge, or comment on a student's pull request or issue, and never show a student's name or work in an image.
  >
  > **Images.** Screenshots are real captures (`AUTHORING.md`, Images). Don't print private individuals' names. Public records name members of the public; count them, don't print them.
  >
  > **Facts that live in more than one place.** Before changing a grade weight, a due date, the `webdata` command, or code copied from a chapter, read `docs/course-facts.md` and change every copy in the same pull request.
  >
  > **Large or unclear requests.** When the instructor writes "AMA", ask a short round of questions before building. Otherwise make the conventional choice and say so in the PR.
- **Why it works:** a new session, or one that has just been compacted, reads the rules from the repository rather than reconstructing them from a summary. It also resolves the rebase-or-merge conflict in writing.
- **Owner:** maintainer review
- **Status:** Proposed
