\begin{frame}{From scraping to APIs}
    For six weeks we \textbf{reverse-engineered} pages built for human eyes --- inspecting HTML, rickety archives, guessing selectors, and cleaning up PDFs.

    \bigskip

    This week begins Part III: \textbf{API-based data access}. Instead of converting web content into data, we ask for the data publishers provide.

    \bigskip

    The skills you build here --- reading documentation, constructing parameterized URLs, handling pagination, parsing nested JSON --- transfer to \textit{every} API in the rest of the course.

    \bigskip

    We have been using the Wikipedia API throughout the course but now we will explore more of what we can do with it
\end{frame}

\begin{frame}{What is an API?}
    An \textbf{API} (Application Programming Interface) is a \textbf{contract}. It specifies what you can request, which parameters you can send, and the format of the response.

    \bigskip

    \begin{itemize}
        \item Clean \textbf{JSON}, not cluttered HTML
        \item \textbf{Stable endpoints}, not fragile CSS selectors (mostly)
        \item \textbf{Documentation} tells you exactly what exists and how to get it
    \end{itemize}

    \bigskip

    The tradeoff: an API only exposes what its operator \textit{chooses} to. You cannot request a field that the API does not include, exceed the rate limits, or rely on the API forever. 

    \bigskip
    
    The ``post-API age'' from Week 03 should land harder now: many APIs have been restricted, repriced, or shut down --- which is frustrating when you see how powerful they can be!
\end{frame}

\begin{frame}{A tour: what sits behind every article}
    Like most users, you have probably never clicked any deeper into Wikipedia than an article. But Wikipedia keeps many important records publicly available:
    \begin{itemize}
        \item who changed what, and when --- the \textbf{revision history}
        \item what editors argued about --- the \textbf{talk page}
        \item how many people read it --- \textbf{pageviews}
        \item what it links to, what links to it, and the same topic in other \textbf{languages}
        \item its \textbf{references}, \textbf{categories}, and \textbf{templates}
        \item the editors themselves --- \textbf{user pages} and \textbf{contributions}
    \end{itemize}
    \bigskip
    Each one has an \textbf{API endpoint}. Anything you can see in the interface, you can count.
\end{frame}

\begin{frame}{The anatomy of a request --- and what the notebook covers}
    \begin{columns}[T]
        \begin{column}{0.46\textwidth}
            Every MediaWiki call is four parts:
            \begin{enumerate}\small
                \item a \textbf{base URL} --- \texttt{.../w/api.php}

\begin{frame}[fragile]{The four parts, then navigate the JSON}
    Assemble the request as a dictionary of parameters; \texttt{requests} builds the URL for you:
\begin{lstlisting}
import requests
url = "https://en.wikipedia.org/w/api.php"
HEADERS = {"User-Agent": "WebDataScience/1.0 (your-email@colorado.edu)"}

params = {"action": "query",                           # what to do
          "titles": "University of Colorado Boulder",  # about this page
          "prop":   "info",                            # what we want back
          "format": "json"}                            # how we want it
data = requests.get(url, params=params, headers=HEADERS).json()
\end{lstlisting}
    Then walk the nested response one key at a time --- page IDs are the keys:
\begin{lstlisting}
pages = data["query"]["pages"]
page_id = list(pages.keys())[0]
print(pages[page_id]["title"], pages[page_id]["pageid"], pages[page_id]["length"])
\end{lstlisting}
\end{frame}

\begin{frame}[fragile]{Revisions --- and the pagination loop}
    \begin{columns}[T]
        \begin{column}{0.6\textwidth}
\begin{lstlisting}
def get_revisions(title, until="2026-09-30T23:59:59Z"):
    params = {"action": "query", "titles": title,
        "prop": "revisions", "rvlimit": "max",
        "rvprop": "ids|timestamp|user|size|comment",
        "rvstart": until,       # newest edit to include
        "format": "json"}
    all_revisions = []
    while True:                 # the pagination loop
        response = requests.get(url, params=params,
                                headers=HEADERS)
        response.raise_for_status()
        data = response.json()
        page = list(data["query"]["pages"].values())[0]
        all_revisions.extend(page.get("revisions", []))
        if "continue" in data:
            params.update(data["continue"])  # next batch
        else:
            break
    return pd.DataFrame(all_revisions)
\end{lstlisting}
        \end{column}
        \begin{column}{0.36\textwidth}
            The most common API bug: \textbf{forgetting to paginate}. The server returns 500 at a time and a \texttt{continue} token when more remain. Skip the loop and you silently keep a \textit{fraction}.

            \medskip
            \texttt{rvstart} fixes the window, so next week's run gives today's answer.
        \end{column}
    \end{columns}
\end{frame}

\begin{frame}[fragile]{Pageviews: a second API}
    \begin{columns}[T]
        \begin{column}{0.56\textwidth}
        The REST API puts its parameters in the URL's \textit{path}. Define the function once:
\begin{lstlisting}
def get_pageviews(title, start, end,
                  agent="user", granularity="daily"):
    article = title.replace(" ", "_")
    url = ("https://wikimedia.org/api/rest_v1/metrics"
           "/pageviews/per-article/en.wikipedia"
           f"/all-access/{agent}/{article}"
           f"/{granularity}/{start}/{end}")
    response = requests.get(url, headers=HEADERS)
    response.raise_for_status()
    views = pd.DataFrame(response.json()["items"])
    views["timestamp"] = pd.to_datetime(
        views["timestamp"], format="%Y%m%d%H")
    return views[["timestamp", "views"]]
\end{lstlisting}
        \end{column}
        \begin{column}{0.4\textwidth}
            Define the function in one cell, and use it in the next:
\begin{lstlisting}
cu_views = get_pageviews(
    "University of Colorado Boulder",
    "20210101", "20260930")
\end{lstlisting}
            \medskip
            No \texttt{continue} here: one request returns the whole range.

\begin{frame}{What a pageview counts}
    \begin{columns}[T]
        \begin{column}{0.42\textwidth}\small
            A pageview is \textbf{not a person}: one reader who reloads three times is three views.
            \begin{itemize}\small
                \item The REST API's counts start in \textbf{July 2015}, under a definition drafted in 2014--15 (\href{https://meta.wikimedia.org/wiki/Research:Page_view}{Research:Page view}).
                \item Before that, \href{https://dumps.wikimedia.org/other/pagecounts-raw/}{pagecounts-raw} (2007--2016) counted every request, edits and crawlers included. A fallback, not comparable.
                \item The \textbf{agent} says who is reading: \texttt{user} (people), \texttt{spider} (crawlers that say so), \texttt{automated} (bots that don't).
                \item When bot detection improves, past counts can be \textbf{reclassified} --- as March--August 2025 were.
            \end{itemize}
        \end{column}

\begin{frame}[fragile]{One function for every other feature}
    Links, categories, templates, languages, backlinks, and contributions are all \texttt{action=query} with a different \texttt{prop} or \texttt{list}. Write the continuation loop once:
\begin{lstlisting}
def query_all(params):
    params = {"action": "query", "format": "json", **params}
    results = []
    while True:
        response = requests.get(url, params=params, headers=HEADERS)
        response.raise_for_status()
        data = response.json()
        results.append(data["query"])
        if "continue" in data:
            params.update(data["continue"])
        else:
            break
    return results

# page_list() runs query_all() for one page and one prop, and returns the items
categories = page_list(title, "categories", "cllimit")
backlinks = query_all({"list": "backlinks", "bltitle": title, "bllimit": "max"})
\end{lstlisting}
\end{frame}

\begin{frame}{Key takeaways}
    \begin{enumerate}
        \item An API is a \textbf{documented contract}: structured, intentional access --- clean JSON and stable endpoints, no reverse-engineering.
        \item The skill transfers: \textbf{read the docs $\rightarrow$ build a parameterized request $\rightarrow$ parse nested JSON} one level at a time.
        \item Always \textbf{paginate}: follow the \texttt{continue} token in a loop, or you silently keep only the first batch.
        \item Be a good client: a descriptive \textbf{User-Agent}, serial requests, and \texttt{maxlag} for bulk jobs (the ethics of Ch.~2, applied). A client such as \textbf{mwclient} does the repetitive parts once you know what they are.
        \item Know what your numbers count: a \textbf{pageview} is not a person, and its definition --- and the bots behind it --- have changed.
        \item Openness is a \textit{choice}, not a guarantee of completeness --- Wikipedia's data still inherits its volunteer community's biases.
    \end{enumerate}
    \bigskip
\end{frame}
